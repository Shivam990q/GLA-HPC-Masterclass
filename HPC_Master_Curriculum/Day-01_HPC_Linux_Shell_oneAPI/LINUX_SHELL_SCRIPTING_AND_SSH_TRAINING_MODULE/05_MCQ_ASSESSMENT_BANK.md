#### Q1. Which statement accurately describes the `/proc` directory in a standard Linux system? [Bloom: Understand]
- A) It is a physical ext4 disk partition where persistent kernel log files are stored.
- B) It is a pseudo/virtual in-memory filesystem generated by the kernel exposing process and hardware states.
- C) It is a temporary cache directory deleted every time the system powers down.
- D) It stores binary executable packages installed by unprivileged non-root users.
> **Correct Answer: B**  
> **Explanation**: `/proc` is a virtual filesystem (`procfs`) mounted in RAM. Files inside it do not consume physical disk space; reading `/proc/cpuinfo` or `/proc/meminfo` queries the live Linux kernel directly. Distractor A is incorrect because `/proc` is not on physical disk. Distractor C describes `/tmp`. Distractor D describes `/usr/local/bin` or `~/bin`.

#### Q2. A user creates a hard link to `data.csv` called `data_link.csv`. If the original `data.csv` is subsequently deleted with `rm data.csv`, what occurs when attempting to read `data_link.csv`? [Bloom: Apply]
- A) The file read fails with `No such file or directory` because the target inode was destroyed.
- B) The file read succeeds and all data is preserved because the underlying inode's link count decremented from 2 to 1.
- C) The file read returns empty bytes (0 bytes) because the file pointer became a dangling pointer.
- D) The operating system automatically restores `data.csv` from the trash recycle bin.
> **Correct Answer: B**  
> **Explanation**: A hard link is a direct directory pointer to an inode. When a file is created, its link count is 1. Creating a hard link increments the inode's link count to 2. Running `rm data.csv` decrements the link count to 1. The kernel only deallocates disk blocks when the link count reaches 0 and no open file descriptors hold the inode. Distractor A describes a broken symbolic (soft) link.

#### Q3. An administrator needs to set permissions on a sensitive database script such that the owner has full read, write, and execute permissions, group members can read and execute, and others have zero access. What is the octal permission value? [Bloom: Apply]
- A) `750`
- B) `755`
- C) `740`
- D) `770`
> **Correct Answer: A**  
> **Explanation**: Owner: $r(4) + w(2) + x(1) = 7$. Group: $r(4) + -(0) + x(1) = 5$. Others: $-(0) + -(0) + -(0) = 0$. Hence, `chmod 750`. `755` gives others read and execute access (insecure). `740` does not grant execution permission to the group.

#### Q4. If the active shell `umask` is set to `027`, what will be the default permissions of a newly created regular text file? [Bloom: Analyze]
- A) `-rwxr-x---` (750)
- B) `-rw-r-----` (640)
- C) `-rw-r--r--` (644)
- D) `-rwxr-xr-x` (755)
> **Correct Answer: B**  
> **Explanation**: By default, regular files have a maximum base creation mask of `666` (no execution bits by default for security). The bitwise calculation: `666 & ~027`:
> - Owner: $6 - 0 = 6$ (`rw-`)
> - Group: $6 - 2 = 4$ (`r--`)
> - Others: $6 - 7 = 0$ (`---`) (masked out completely)
> Result: `640` (`-rw-r-----`). Directories start from base `777`, which would result in `750`.

#### Q10. What is the fundamental difference between sending `kill -15 <PID>` and `kill -9 <PID>` to a misbehaving process? [Bloom: Understand]
- A) `kill -15` (SIGTERM) requests polite termination allowing the process to catch the signal and clean up resources; `kill -9` (SIGKILL) forces immediate kernel termination and cannot be caught or ignored.
- B) `kill -9` asks the process to save its state to disk; `kill -15` deletes the executable binary from the drive.
- C) `kill -15` requires root permissions; `kill -9` can be sent by any unprivileged user.

> **Correct Answer: A**  
> **Explanation**: SIGTERM (15) is the default cooperative signal. The application can catch it, flush file buffers, release locks, and close database connections. SIGKILL (9) is handled directly by the kernel scheduler; the process table entry is wiped immediately without process notification.

#### Q18. Inside a Bash function, what is the exact difference between iterating over `"$@"` versus `"$*"` when parameters contain spaces (e.g., `"arg 1" "arg 2"`)? [Bloom: Analyze]
- A) There is no difference; both expand identically.
- B) `"$@"` preserves each positional argument as an individual quoted word (`"arg 1"` and `"arg 2"`), whereas `"$*"` concatenates all arguments into a single unified string separated by the first character of `$IFS` (`"arg 1 arg 2"`).

> **Correct Answer: B**  
> **Explanation**: `"$@"` expands to `"$1"` `"$2"` ... `"$N"` maintaining separate argument boundaries. `"$*"` collapses them into `"$1c$2c...$N"` where `c` is the first character of `$IFS` (typically space).

#### Q20. What is the difference between `cmd > file 2>&1` and `cmd 2>&1 > file`? [Bloom: Analyze]
- A) They are completely interchangeable; both redirect stdout and stderr to `file`.
- B) `cmd > file 2>&1` redirects stdout to `file`, then duplicates stderr to stdout (both go to `file`). `cmd 2>&1 > file` duplicates stderr to the current terminal stdout *before* stdout is redirected to `file`, so stderr continues printing to the screen!
- C) `cmd 2>&1 > file` crashes with a syntax error.
- D) `cmd > file 2>&1` is only supported in Python, not Bash.
> **Correct Answer: B**  
> **Explanation**: Redirections are evaluated left to right. In `2>&1 > file`, descriptor 2 is pointed to wherever descriptor 1 currently points (the console). Then descriptor 1 is redirected to `file`. As a result, stderr prints to console, not `file`.

#### Q21. Which syntax performs native integer arithmetic in modern Bash without spawning external subshell processes? [Bloom: Remember]
